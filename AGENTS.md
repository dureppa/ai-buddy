# Инструкции для агентов

## Перед началом задачи

1. Открой [оглавление документации](docs/README.md) и прочитай [архитектуру](docs/architecture.md), [стек проекта](docs/stack.md), описание каждого затронутого компонента и относящиеся к задаче спецификации в `docs/`. Для изменений кода прочитай [стандарты разработки](docs/engineering.md).
2. Проверь рабочее дерево. Для каждой задачи создай отдельную ветку от актуальной `origin/main` в текущем checkout или в отдельном Git worktree. Если в checkout есть чужие незакоммиченные изменения, используй worktree, чтобы сохранить их. Называй ветки в формате `тип/что-меняется`, например `feature/onboarding-checklist`, `fix/access-request-status`, `docs/project-workflow` или `ci/automatic-delivery`.
3. Если меняешь поведение AI Buddy или его инструментов, опиши ожидаемое поведение и ошибки в спецификации до реализации.

## Стек и источники

- Соблюдай [стек AI Buddy](docs/stack.md). Go и PostgreSQL отвечают за бизнес-операции и данные, Python с Flask за AI, MCP за вызовы инструментов, React и TypeScript за веб и UI расширения. Используй [материалы кейса](docs/avito-sources.md) и [AvitoTech Playbook](https://github.com/avito-tech/playbook/blob/master/development-principles.md) при проектировании.
- Для задачи сначала используй уже подключённые библиотеки и версии, закреплённые в манифестах репозитория и lock-файлах. Если нужна новая библиотека, начни с подходящих вариантов из [материалов Авито](docs/avito-sources.md) и проверь совместимость со [стеком проекта](docs/stack.md). В PR объясни, зачем нужна новая зависимость, и обнови манифест и связанный lock-файл или `go.sum`.
- Для фронтенда используй [правила работы с макетами и компонентами](docs/components/web.md). Ориентируйся на веб-стили, варианты компонентов и спецификации из [материалов дизайн-системы Авито](https://habr.com/ru/companies/avito/articles/543450/).
- Локальную разработку Python веди в `ai-agent/.venv`. Из каталога сервиса выполни `uv sync --locked` и запускай команды через `uv run --locked`. Используй uv для изменений зависимостей и коммить `pyproject.toml` и `uv.lock` вместе. Правила установки для Go и фронтенда описаны в [стеке проекта](docs/stack.md).

## Код и тесты

- Определяй границы работы по задаче и ответственности компонентов. Если изменение затрагивает взаимодействие веба, расширения, Go API, PostgreSQL, Python AI-сервиса или MCP, согласуй форматы данных и поведение на границах и обнови затронутые контракты в `contracts/` и спецификации в `docs/`.
- Следуй соглашениям компонента. Используй понятные имена, сохраняй существующие контракты и проверяй входные данные на границах приложения.
- Покрывай каждую новую функцию или метод тестами. Проверяй наблюдаемое поведение напрямую или через публичный интерфейс, который выполняет эту функцию. Для исправлений добавляй регрессионные тесты. Проверяй основной путь, ошибки и граничные случаи, которые применимы к изменению.
- При добавлении тестов проверь, что CI запускает их при создании и обновлении PR. Если существующая job их не подхватывает, обнови команду, конфигурацию или набор jobs в том же PR.
- Для Python используй аннотации типов, mypy, Ruff и pytest. Для Go используй типизацию компилятора, gofmt, go vet и стандартный пакет `testing`. Команды, правила для тестов и ссылки на официальные руководства собраны в [стандартах разработки](docs/engineering.md).
- Запускай проверки затронутых компонентов, включая проверки контрактов при изменении API. Указывай в PR фактические команды, результаты и причины пропуска применимых проверок.
- Для небольшого изменения в документации или локальной правки без влияния на код можно выполнить только относящиеся к ней проверки. Полный набор проверок запускается CI при создании или обновлении PR.
- Для большого блока или изменения, которое может повлиять на другие компоненты, кроме тестов нового функционала запусти затронутые зависимые тесты и полный `just check`. В PR укажи, какие проверки выполнены локально, а какие оставлены CI.

## Документация и инфраструктура

- В том же PR обновляй все документы и служебные файлы, которых касается изменение. Проверь `README.md`, описание каждого затронутого компонента, спецификации сценариев и контракты. Если меняются команды запуска или проверки, зависимости, настройки или развёртывание, синхронизируй затронутые скрипты, `justfile`, `.env.example`, `docker-compose.yml` и CI.
- Поддерживай актуальными назначение компонентов, точки входа, карту важных файлов, зависимости, настройки и команды запуска и тестов. Если создаёшь новый компонент, добавь его документ в [оглавление](docs/README.md).

## Документация, тесты и критерии кейса

Жюри считает текущим описанием `README.md`, [маршрут проверки](docs/demo.md), [ответы на критерии](docs/criteria.md) и [отчёт о покрытии](docs/coverage.md). Эти файлы должны описывать одно поведение.

Когда меняешь код:

1. Если меняется поведение агента или его инструментов, обнови спецификацию в `docs/specs/` в том же изменении. В ней должны быть видны момент подтверждения человеком, что уходит в сервис и какая ошибка возвращается.
2. Обнови документ затронутого компонента. Если меняются запуск, учётки, модель или команды проверки, обнови `README.md` и `docs/demo.md`.
3. Если изменился ответ на критерий кейса, поправь `docs/criteria.md`. Не оставляй в инструкциях второй, уже неработающий способ запуска.
4. Удали абзацы и файлы, которые описывают прежнее поведение как текущее. Не добавляй «исторический» раздел, который противоречит инструкции запуска. Каталог `openspec/changes/` — архив предложения, не инструкция для жюри и не источник актуальных команд.
5. Покрой новое поведение тестом. Порог относится к прикладному коду `web/frontend`, `web/backend` и `ai-agent`: каждый контур выше 80%, проценты не усредняй. Имитации в `corporate-services/` и `tools/` в этот порог не входят. После измерения обнови `docs/coverage.md`: дата, команда, что измеряется, что исключено и фактические числа. Не переноси числа из старых отчётов и не придумывай их.
6. Не документируй неизмеренное: время интерфейса, эффект для стажёров, качество модели на holdout. Метрики пользы в `docs/criteria.md` остаются предложением, пока нет отдельного прогона.
7. Продуктовый запуск использует DeepSeek. Не добавляй в инструкции другого провайдера. Ключ модели не коммить.

## Коммиты и pull request

- Оформляй заголовок каждого коммита как `тип(область): пояснение`. Например, `feat(agent): show access request status` или `docs(repo): document development workflow`. В теле коммита при необходимости поясни причину, существенные детали и результаты проверок.
- Перед коммитом просмотри подготовленные изменения и выполни `git diff --cached --check`. Перед пушем проверь итоговый diff ветки задачи относительно `origin/main`. Изменения в `main` проходят через PR.
- После завершения изменений по задаче сделай коммит, запушь ветку и создай PR, не ожидая отдельной просьбы пользователя. Не сливай PR автоматически без запроса на слияние.
- После пуша создай PR в `main` и заполни [шаблон PR](.github/pull_request_template.md). При использовании GitHub CLI передай заполненный текст через `gh pr create --body-file`.
- Автор с правом слияния может самостоятельно слить свой PR после прохождения обязательных проверок. Ревью от [`CODEOWNERS`](.github/CODEOWNERS) можно запросить при необходимости.
- PR в `main` нельзя сливать без успешных обязательных CI jobs `frontend`, `python`, `go` и `repository`. Если check ещё выполняется или завершился ошибкой, сначала исправь причину и обнови PR.
