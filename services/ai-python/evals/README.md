# Эталонные примеры knowledge-v1

[knowledge-v1.json](knowledge-v1.json) — начальная **черновая**, а не утверждённая человеком gold-разметка компонента проверки знаний. 6 development-кейсов и 2 кандидата в holdout по отдельным семействам. Версии, ответы, рубрики и ожидаемые оценки хранятся раздельно. Ожидаемые verdicts/recommendation никогда не передаются оценщику; поле criteria.expected в запросе — сама рубрика знаний, необходимая для проверки ответа, а не эталонная оценка конкретного примера.

Это компонентный старт. Общий кандидат golden dataset уже подготовлен отдельно: [agent-v1 — 20 development / 10 candidate holdout](agent-v1/README.md), без live-прогона и без переноса старых примеров в новый holdout. Метки нужно проверить команде/наставнику, обсудить спорные fail/unclear и затем заморозить версию. Обновление разметки должно иметь причину, не подгоняться к ответу модели.

## Два разных вида проверки

1. pytest со scripted LLM проверяет схемы, цитаты, агрегацию, отказы и запрет автоматического одобрения. Валидация структуры и согласованности меток читает оба split, но не вызывает модель. Это не метрика смыслового качества и не live-прогон holdout.
2. `uv run --locked python -m experiments.assessment_eval` вызывает реальный Flask endpoint и локальную LLM на development. Результат сохраняется в отдельный файл с версией промпта и временем запуска; complete=true появляется только после полного прогона. Holdout можно вызвать отдельно через `--split holdout`, но для этого среза он **не запускался**. После просмотра holdout его нельзя использовать для дальнейшей настройки и одновременно считать независимым тестом.

## Что измеряется

- Полное совпадение набора criterion verdicts и совпадение recommendation отдельно.
- Количество опубликованных ложных pass: модель дала pass там, где эталон fail/unclear. Отказ 503 не считается правильной оценкой и уменьшает качество/доступность, даже если ложных pass при нём нет.
- Проверка обязательности наставника и отсутствия полей approved/completed/advance_stage.
- HTTP/timeout ошибки, длительность, method=llm либо rule_guard.

Правила пустого ответа/вредоносных инструкций дают unclear без модели. Их успех нельзя включать в оценку точности именно LLM без отдельного отчёта: необходимо показывать модельные случаи и guards раздельно.

## Как поддерживать качество

Утвердить рубрику и метки с наставником; расширить типичные/пограничные/негативные примеры; добавлять реальные ошибки как регрессии; версионировать модель/quantization/prompt/dataset; сравнивать новую версию с baseline на одинаковых кейсах. Перед выпуском отдельно согласовать пороги качества и запрет критичных ложных оценок. Для редких случаев и спорных ответов остаётся ручная проверка. Метрики на этих нескольких development-примерах не доказывают общий уровень качества.

Это не требует LangChain/LangSmith: JSON, pytest и отдельный CLI достаточны для старта. [Evaluation concepts](https://docs.langchain.com/langsmith/evaluation-concepts) описывает общую практику разметки и разделения offline/online проверок; новый внешний сервис в проект не подключался.
