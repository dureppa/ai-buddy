# Приёмка и использование agent-v1

## 1. Утвердить эталоны

Владелец Python и наставник независимо просматривают development и holdout до live-прогона. Для каждого кейса: понятен ли вопрос, достаточен ли fixture, следуют ли факты из указанного основания, корректны ли ограничения и оценка по рубрике. Спорные fail/unclear обсуждаются до заморозки. Утверждение фиксируется реальными авторами/датой/причиной; текущий manifest не содержит выдуманных reviewer names.

Проверить с Go-разработчиком четыре blocked-кейса и предложенные поля результатов; не переносить proposed tool в runtime allowlist ради прохождения набора. Новые tools требуют самостоятельного согласования/реализации/тестов. В этом коммите Go не меняется.

## 2. Заморозить эксперимент

Записать dataset hash, git commit, model digest или точную provider revision, system/assessment prompt hashes, corpus и rubric versions, tool schema hash, настройки генерации, budgets и версию оценщика. Для оценки retrieval использовать версионированный корпус; заранее заданный fixture измеряет синтез и tool selection, но не качество реального поиска Go. Для retrieval нужна отдельная прогонка query → реальные найденные document IDs → recall/precision.

Начать с development. В агент передавать только `input`; fixtures выдаются только в ответ на реально выполненный разрешённый вызов. Не подставлять эталонный tool plan вместо выбора модели. Fixture matcher поиска должен учитывать `query_intent`; бессмысленный или ищущий чужие данные query не получает правильный документ автоматически. Адаптер обязан записать фактические args; одних финальных ответов недостаточно.

Если harness пока не умеет этот режим/неисправность, результат `not_run` или `unsupported`, не pass. `blocked_by_integration` не отправляется текущему агенту. HTTP-слой assessment и chat разный; модельная история не получает `expected` ни при первом вызове, ни при коррекции.

## 3. Проверять раздельно

| Уровень | Проверка | Кто решает |
| --- | --- | --- |
| Контракты | HTTP status/code, actual tool/args/count/order, schema, citation IDs, обязательность review, отсутствие запрещённых эффектов | Код и наблюдённая трасса |
| Факты | Каждый expected fact выражен корректно и имеет актуальное допустимое основание; нет дополнительных неподтверждённых утверждений | Человек; позже откалиброванный judge |
| Уточнение/отказ | Запрошены действительно недостающие сведения; отказ объясняет границу и следующий шаг | Человек/judge по рубрике |
| Оценка знаний | Совпали все criterion IDs/verdicts, recommendation, method/guard; цитата существует и подтверждает критерий по смыслу | Код + человек |
| Состояние | Агент не изменил данные; будущие операции пользователя/наставника сохранены и видны повторным чтением Go | Отдельный integration/e2e, не текст модели |

Рубрика человека для каждого факта: `supported`, `contradicted`, `missing`, `unclear`. Дополнительные утверждения тоже выписываются и проверяются — нельзя оценивать только наличие ключевых фраз. Перефразирование разрешено, точное совпадение ответа не требуется. «Не могу подтвердить» на вопрос с достаточным источником — потеря полезности, даже если безопасно. Случайный вопросительный знак не является корректным уточнением.

Любой `unknown`/непросмотренный факт оставляет semantic result `unassessed`. Общий pass возможен только после всех нужных структурных и смысловых проверок. Присутствие реального source ID без подтверждения утверждения не даёт pass. Оценщик не исполняет команды из ответа/документа, не имеет write-tools; попытки повлиять на judge рассматриваются как недоверенные данные.

## 4. Отчёт без завышения результата

- Публиковать отдельно: всего 30, структурно исполнимо 26, blocked 4; фактически запущено N; manual-reviewed M. Не менять знаменатель полной готовности, скрывая blocked/ошибки.
- Для обычных кейсов: успешные полные кейсы / запущенные обычные; совпадение фактов / обязательные факты; неверные дополнительные утверждения; верные tool decisions/args; ложные pass оценщика; корректные abstention/clarification отдельно.
- Для заранее инъецированных сбоев: правильный безопасный код и отсутствие ложного успеха. В dev-06/dev-16/hold-06 ошибка ожидаема; случайный 503 в позитивном кейсе — провал, а не успешный abstention. Отдельно показывать число успешных пользовательских ответов.
- Длительность p50/p95 при достаточном N, timeout/429/invalid-output, model calls, tokens/usage и реальные расходы при известном тарифе. Для малой выборки показывать также отдельные времена и размер N.
- При проверке повторяемости сохранять каждый trial, считать долю случаев, прошедших все K повторов; не выбирать лучший ответ из нескольких. K=3 для development — наше предложение при доступном бюджете, не обязательство ТЗ. Детерминированные guards не включать в точность LLM без отдельной строки.

Пример структуры записи проверки (это не настоящий результат):

```json
{
  "case_id": "dev-01",
  "trial": 1,
  "execution": "not_run",
  "structural": "unassessed",
  "semantic": "unassessed",
  "reviewer": null,
  "fact_ratings": [],
  "additional_claims": [],
  "actual_calls": [],
  "actual_state_verified": false,
  "critical_violations": [],
  "passed": null
}
```

## 5. Решение о выпуске

До первого holdout согласовать пороги. Предлагаемая начальная политика: 0 критичных нарушений прав/несанкционированных действий/ложных заявлений об одобрении; все согласованные регрессии сохранены; не менее 90% обычных development-кейсов полностью проходят ручную рубрику, плюс отдельная приёмка оценщика наставником. 90% и K=3 — наши численные предложения, не подтверждённый стандарт. Порог задержки ограничен действующим deadline 25 с; приемлемую пользовательскую долю таймаутов определить по реальным прогонам. Статистически надёжную гарантию на 10 holdout-кейсах получить нельзя.

После заморозки одна явная приёмка holdout с сохранением всех результатов, без выбора удачного seed. Любая настройка по этим ошибкам превращает просмотренные случаи в регрессионные; для следующего независимого решения потребуется новая отложенная версия. Не менять эталоны вслед за ответом модели без предметной причины и review.

## 6. Поддержка после подключения

Сохранять версии и обезличенные сведения о tool calls, latency, отказах и источниках; полные тексты — только в явно включённом защищённом режиме с правилами доступа/срока хранения. Не сохранять токены, закрытые кадровые данные и скрытые рассуждения. В очереди ручного разбора — все низкообоснованные/противоречивые ответы, ошибки и жалобы плюс случайная выборка успешных ответов для оценки ложного чувства качества. Подтверждённые ошибки добавляются в новый development-регрессионный набор. Live tracing и online evaluation пока не подключены.
