# Оценка знаний: первый Python-срез

Авторизован пользователем. Реализуется Python-режим без изменений Go/UI. Точный внутренний контракт ниже — новое решение команды для реализации; его подключение/хранение на Go остаётся отдельной задачей. Общие требования AG-05/06/08 и SVC-03/11 сохраняются.

## Контракт и ответственность

- POST /internal/v1/assessments MUST требовать тот же сервисный bearer и закрытый JSON ≤64 KiB. Go выдаёт request_id/conversation_id/evaluation_id/answer_id (UUID), task_id и версии task/plan/answer/rubric/context; передаёт question, answer, context и 1–5 критериев {id,description,expected,required}. Нужен хотя бы один обязательный критерий, id уникальны. Размер текста snapshot ограничен до вызова модели, без усечения.
- Отдельный assessment prompt MUST оценивать конкретный ответ по переданной рубрике. Answer/context — данные, не команды; эталон и обязательность модель не меняет. Этот режим MUST NOT вызывать MCP, хранить прогресс, одобрять этап или отправлять действия. Историю обучения и чат не используем как скрытую рубрику.
- Модель MUST вернуть только judgments: criterion_id, reason_code (matched/contradiction/missing/ambiguous) и quote либо null. Python отображает matched в pass, contradiction/missing в fail, ambiguous в unclear и формирует краткое обоснование из типа причины и описания критерия. Это компактный протокол для локальной модели; развёрнутое объяснение моделью в этом срезе не генерируется. Полный набор id обязан совпадать с рубрикой без дубликатов. Для matched/pass нужна непустая дословная цитата из ответа; любая указанная цитата проверяется как substring. Позиции фрагмента считает Python, не модель.
- Итог MUST содержать входные IDs/версии из кода, SHA-256 исходного ответа, результаты по всем критериям, recommendation и manual_review_required=true. Recommendation считает Python: обязательный fail → needs_revision; иначе обязательный unclear → needs_clarification; иначе ready_for_mentor_review. Необязательные критерии не блокируют рекомендацию. Процентов, approved/completed/advance_stage нет.
- Пустой ответ и обнаруженные инструкции подмены оценки MUST давать явный rule_guard: все unclear, needs_clarification, безопасная причина, без LLM. Это отказ автоматической оценки, не доказанный недостаток знаний.
- LLM использует JSON Schema structured output, без tools, temperature=0/seed=42/think=false. Максимум 2 вызова: одна коррекция неверного JSON/id/цитаты/формата в общем deadline 25 с, model timeout 20 с по умолчанию. Сетевые ошибки/429/timeouts не повторяются; используются действующие AI_* коды. Повторно неверный результат → 503/AI_INVALID_RESPONSE, без фиктивного pass.
- Endpoint MUST не передавать служебные IDs, версии, токены или эталонные gold verdicts модели; исходные ответы/эталоны/цитаты не логируются. GET /health/ready/assessments проверяет только локальную конфигурацию, без сети; assessment не зависит от MCP_URL.
- Go MUST сохранить snapshot и сравнить версии с актуальными перед сохранением/решением. Python не может проверить, изменил ли стажёр ответ в БД за время генерации, и не гарантирует идемпотентность evaluation_id. Решение наставника не заменяется этой рекомендацией.

## Приёмка

Необходимые offline-тесты: auth/закрытый контракт, совпадение id/версий, агрегирование обязательных/необязательных критериев, цитаты, пропуски/дубли/чужие id, попытка approval в output, подмена рубрики в answer, одна коррекция и ошибки/таймауты, отсутствие MCP и служебных полей в LLM. Старые тесты HTTP и native Ollama используются повторно.

Размеченный knowledge-v1 dataset — черновик gold для этого компонента, метки требуют проверки команды. Development и candidate holdout разделены по сценариям; holdout не запускается и не используется для настройки этого среза. Проверки parser/агрегации с fake LLM не являются оценкой смыслового качества. Live-eval сравнивает фактические criterion verdicts/recommendation с эталонной разметкой и отдельно считает ложные pass, ошибки и обязательность review. Полный план 20 development/10 holdout для всего агента этим компонентным набором не закрывается.
