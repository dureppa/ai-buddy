# Golden dataset всего агента: первый набор

Авторизован пользователем 13.11.2026. Только Python evaluation assets и документация. Runtime агента, Go и UI не меняются; платные вызовы и live holdout не выполняются.

## Формат и границы

- Версия agent-v1 MUST содержать ровно 20 development и 10 candidate holdout кейсов. Разметка draft_requires_team_review: подготовка эталонов не означает одобрение наставника. Существующий knowledge-v1 остаётся отдельной компонентной регрессией, в новый holdout его примеры не копируются.
- Каждый кейс MUST содержать requirement IDs, независимое scenario family, профиль/роль/права/этап, версии, HTTP-вход без gold labels, MCP fixtures или явную неисправность, ожидаемые факты с проверяемыми указателями на fixture/вход/правило, допустимые вызовы и ограничения, допустимые источники и ожидаемые побочные эффекты. Источник синтетического правила MUST NOT объявляться регламентом Авито.
- Для search_knowledge эталон MUST задавать намерение запроса и пример аргументов, а не требовать точную строку query. Для остальных инструментов задаются точные аргументы; порядок проверяется только при зависимости. Схемы реализованных tools проверяются по текущему CONTRACTS. Ожидания для предложенных progress/evidence tools MUST быть явно blocked_by_integration, без исполнения неизвестных tools.
- Кейсы assessment MUST использовать отдельный AssessmentRequest и эталонные criterion verdicts/recommendation вне входа; MCP-вызовы запрещены. Ответы и рубрики нового holdout отличны от прежнего knowledge-v1.
- Development/holdout MUST не пересекаться по scenario family и точным входам; общие сервисы/ограничения допустимы. Это разделение сценариев внутри проекта, не доказательство статистической независимости или внешнего blind benchmark. Полный holdout доступен в Git, поэтому доступ к нему и tuning-history требуют дисциплины команды.

## Проверки и качество

Offline audit MUST проверять количество, уникальность, ссылки на требования/доказательства, соответствие схемам, ограничения шести сервисов и статус заблокированных кейсов. Он MUST NOT публиковать accuracy/pass rate LLM. Валидация обоих split не является live-eval. По умолчанию загрузчик отдаёт только development.

Смысловые факты и запреты MUST проверяться отдельно от структурных ошибок/цитат. Недостаточная трасса, отсутствие ручной разметки и blocked-case означают unassessed/blocked, не pass. Реальный успешный сценарий требует наблюдённого состояния Go, а не текста модели. При проверке подтверждений ожидаемый переход запрещён до одобрения наставника; поздние версии не дают права переписать человеческое решение.

Прогон MUST сохранять code commit, model digest/provider revision, prompt/corpus/dataset/tool-schema versions, вход/финальный ответ и допустимую обезличенную траекторию, фактические usage/cost/timeouts. Не логировать скрытые рассуждения/токены делегации. Ошибки считать отдельно; на обычном кейсе 503 не является правильным ответом, на специально инъецированном отказе безопасный код — ожидаемое поведение. В отчёте разделять эти группы.

Численные release thresholds и число повторов — предложения команды до утверждения. Holdout запускается после заморозки конфигурации и порогов; исправление по обнаруженной holdout-ошибке требует новой отложенной выборки. Никакой runtime-оценщик или внешняя observability-платформа этим блоком не подключается.
