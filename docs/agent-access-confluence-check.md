# Проверка серверных доступов и Confluence

Проверено 15 ноября 2026 локально, PostgreSQL 17, Go 1.27.4, Node 24.22.3,
Python из uv.lock. Новых зависимостей нет. Ожидаемое поведение: [SDD 007](specs/007-agent-access-confluence.md).

## Автоматические проверки

`TEST_DATABASE_URL=... JIRA_TEST_DATABASE_URL=... just check`:

- Jira `go vet`, `go test -race` — успешно.
- `just frontend-check` — формат, ESLint, TypeScript, 118 тестов трёх workspace,
  сборка веба, расширения и всех корпоративных сайтов, включая Confluence — успешно.
- `just python-check` — locked sync, Ruff, mypy, 428 pytest — успешно.
- `just go-check` — gofmt, vet, все тесты, race, coverage — успешно.
  Portal на первом полном прогоне: 84.9% statements.
- HR consents race и repository checks — успешно.
- `compose-check` не запущен: в среде отсутствует команда docker. Проверку
  конфигураций Compose выполняет repository job CI; контейнерная сборка локально не проверялась.

После последней правки и объединения свежего main полный `just check` повторён
с тем же результатом (остановка только на отсутствующем Docker). Проверены
rollback/reapply миграции без удаления профилей и регрессия:
решение по заявке старше последних 100 записей остаётся доступным по id.

## Сквозной сценарий по TCP

Запущены настоящий Go API, Flask DirectRunner, MCP SDK/server в go_http и временная
PostgreSQL со всеми миграциями и seed. Модель заменена управляемым ответчиком:
get_access_catalog → submit_access_request. Ни ключ провайдера, ни реальная LLM
не использовались; это проверка интеграции, не оценка качества модели.

Повторный прогон после объединения main также прошёл.

1. Демосессия Ольги → POST chat/messages с явным «Оформи доступ…», DWH,
   delivery.orders_mart, read, 30 дней, рабочее обоснование и цель исследования.
2. Flask/MCP вызвали серверную операцию. Ответ содержит сохранённую ДОС-000001,
   submitted и ссылку на портал; номер подтверждён записью PostgreSQL origin=agent.
3. Повтор с новым turn вернул тот же id; в очереди одна запись.
4. На информационный вопрос discovery не объявляет submit_access_request;
   get_knowledge_page вернул страницу Доставки, ответ принят с источником Confluence.
5. У Ольги 10 видимых страниц (2 своего продукта и 8 общих); чужой продукт — 404,
   попытка запросить travel.orders_mart — 403.

## Браузер

Вход через штатный Buddy → Confluence 5191: пространство Доставки, дерево страниц,
гайд «Как запросить доступ» и версия/дата загружены из API. В портале 5190 открыта
«Мои заявки»: ДОС-000001, DWH, delivery.orders_mart, чтение, 30 дней, на согласовании.
Выдуманных локальных записей и fallback при ошибке API нет.

## Границы

Заявки и Confluence используют существующую БД Buddy. Сайт Confluence доступен
из «Инструментов и доступов» новой вкладкой. Корпус содержит 16 учебных страниц;
редактор и загрузка корпоративных документов не реализованы. Согласование не
выполняет provisioning. Demo-mode сохраняет прежний упрощённый вход по профилю;
production SSO/ACL не заявляется. Старый localStorage портала не мигрируется.

После второго обновления main (оформление ответов) `just frontend-check python-check`
прошёл: 118 frontend и 428 Python тестов. Отдельно 7 тестов заявки/представления
подтвердили, что номер и статус receipt сохраняются, технический id убирается
из текста, а источник остаётся в реестре. Первый CI PR #53 успешно выполнил все
четыре jobs, включая Compose; обновлённая ветка повторно проходит тот же CI.
