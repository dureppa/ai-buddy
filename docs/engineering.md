# Стандарты разработки

Установку зависимостей см. в [стеке проекта](stack.md). Применяй проверки к коду компонента по мере его появления.

## Тесты на любом языке

- Покрывай новую функцию тестом, который проверяет результат, изменение состояния или ожидаемую ошибку. Дополняй существующие тесты, если они уже проверяют подходящий публичный сценарий.
- Для API, MCP, хранения данных и других границ компонентов добавляй тесты контракта или интеграционные тесты, когда меняется взаимодействие. Для AI-сценария проверяй также выбор инструмента, его аргументы и поведение при отказе или таймауте, если это предусмотрено спецификацией.
- Делай тесты воспроизводимыми. Используй фиксированные входные данные и подмены LLM или корпоративных API в автоматических проверках. В тестах исправлений воспроизводи исходную ошибку и проверяй исправленный результат.
- К сдаче подготовь воспроизводимый отчёт с покрытием строк прикладного кода выше 80% без зависимостей, сгенерированного кода и самих тестов. В отчёте указывай, что именно измеряет инструмент. Например, встроенный отчёт Go показывает покрытие операторов. [Покрытие в Go](https://go.dev/doc/build-cover)

## Python

- Оформляй код в стиле PEP 8 с учётом настроек Ruff. Аннотируй аргументы и возвращаемые значения новых функций. Для данных из HTTP, MCP и LLM проверяй форму и значения при получении. Аннотации помогают статической проверке, а входные данные проверяются при выполнении. [PEP 8](https://peps.python.org/pep-0008/), [mypy](https://mypy.readthedocs.io/en/stable/getting_started.html)
- Группируй проверки однотипных входов через параметризацию pytest. Используй фикстуры для повторяющейся подготовки и очистки состояния. [Параметризация pytest](https://pytest.org/en/latest/how-to/parametrize.html), [фикстуры pytest](https://pytest.org/en/latest/how-to/fixtures.html)

| Команда из `services/ai-python/` | Проверка |
| --- | --- |
| `uv run --locked ruff format --check .` | Форматирование. |
| `uv run --locked ruff check .` | Линтинг. |
| `uv run --locked mypy .` | Строгая статическая проверка типов по настройкам `pyproject.toml`. |
| `uv run --locked pytest` | Тесты. При подготовке отчёта используй pytest-cov с областью прикладного кода. |

[Форматтер Ruff](https://docs.astral.sh/ruff/formatter/), [линтер Ruff](https://docs.astral.sh/ruff/linter/)

## Go

- Используй конкретные типы и обрабатывай возвращённые ошибки. Передавай `context.Context` первым параметром в операции, которым нужны отмена или дедлайн, и сохраняй контекст входящего запроса при обращении к другим сервисам. [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments)
- Пиши тесты в `*_test.go` со стандартным пакетом `testing`. Для нескольких вариантов одного поведения используй табличный тест и именованные подтесты через `t.Run`. В сообщении об ошибке показывай вход, фактический и ожидаемый результат. [Go Test Comments](https://go.dev/wiki/TestComments)

| Команда из `services/backend-go/` | Проверка |
| --- | --- |
| `gofmt -l .` | Список файлов, которым нужно форматирование. Ожидается пустой вывод. |
| `go vet ./...` | Статический анализ подозрительных конструкций. |
| `go test ./...` | Компиляция с проверкой типов и запуск тестов. |
| `go test -race ./...` | Поиск гонок при изменениях конкурентного кода в поддерживаемой среде. |

[Инструменты Go](https://go.dev/doc/cmd), [детектор гонок](https://go.dev/doc/articles/race_detector)

## Веб и расширение

- Используй TypeScript в строгом режиме и проверяй внешние данные на границе API. Для серверного состояния веба используй TanStack Query, для проверки формы ответа и входных данных — Zod.
- Добавляй тесты на Vitest для логики, обработки ответов и состояний интерфейса. Настрой `tsc --noEmit` и `vitest run` при появлении конфигурации и исходников. [Vitest](https://vitest.dev/guide/)
- Текущая фронтенд-версия работает с локальным demo-adapter. Не подменяй его фиктивным HTTP-сервисом внутри `apps/web` и не переноси сюда Go или Python логику. API-клиент подключится отдельной задачей по [OpenAPI-контракту](../contracts/openapi.yaml).
- Проверяй веб и расширение командами `npm run typecheck --workspaces`, `npm test --workspaces`, `npm run build --workspace=@ai-buddy/web` и `npm run build --workspace=@ai-buddy/extension`.

## Полный локальный набор

Запусти `just check`, чтобы выполнить форматирование, ESLint, TypeScript, Vitest, сборку веба и расширения, проверки Python и Go и контроль репозитория. Для отдельных задач доступны `just frontend-check`, `just python-check` и `just go-check`.

CI запускает эти проверки отдельными jobs `frontend`, `python`, `go` и `repository`. Для небольших изменений документации достаточно проверить затронутые файлы. Для изменений, которые затрагивают несколько компонентов, запускай полный набор локально.

## Ревью pull request

PR в `main` должен получить одобрение любого одного code owner из [`.github/CODEOWNERS`](../.github/CODEOWNERS). Список code owners хранится в репозитории и может меняться вместе с командой. Автор PR не может засчитать собственное одобрение. После одобрения и успешного прохождения обязательных jobs `frontend`, `python`, `go` и `repository` PR можно сливать.
