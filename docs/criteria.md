# Ответы на критерии кейса

Документ описывает то, что запускается из этого репозитория. Числа эффекта для стажёров здесь не измерялись. Базовых цифр «было / стало» Авито для кейса не передавало.

Связанные тексты: [README](../README.md), [маршрут проверки](demo.md), [покрытие](coverage.md), [действия агента](components/service-actions.md), [архитектура](architecture.md).

## Допуск

Прототип запускается командой из README. На чистом Docker Compose с живым
DeepSeek пройден основной сценарий заявки под Ольгой Соколовой и проверен
отказ под Александром Кимом. [Результаты и шаги](demo.md#приёмка-на-чистом-стенде).
Продуктовый PDF команда сдаёт отдельно: без него кейс не допускает решение
к оценке.

## 30% — внедряемость и интеграции

Buddy не заменяет кадровые системы. Он вызывает их учебные API. Боевой адрес подставляется вместо нашего, контракт остаётся границей: публичные схемы лежат в `contracts/`. Угадывать закрытые API Авито не требуется.

| Уже есть в Авито | Как сделано в прототипе |
| --- | --- |
| Go, PostgreSQL, Python и Flask | Go API и данные в PostgreSQL, агент на Flask |
| React, TypeScript, TanStack, Zod | Веб Buddy. Zustand не подключён: общего клиентского хранилища, ради которого он нужен, нет |
| Docker, CI | `docker-compose.yml` и GitHub Actions |
| MCP и спецификации поведения | Python MCP, SDD в `docs/specs/` |
| Отсутствия, командировки, найм, увольнения, согласия, бенефиты, чек-лист | Отдельные учебные сервисы и чек-лист в вебе |
| Jira, Confluence, Mattermost и другие инструменты команды | Отдельные учебные сервисы в `tools/` |
| Авторизация и роли | Демосессия без пароля и проверка прав текущего профиля на каждом чтении и действии |
| Redis, Kafka, Grafana, Clickstream, ИИ-крон, feature flags | Не поднимаются: для выбранных сценариев нет отдельной задачи кеша, шины или флагов |

Модель проверки — DeepSeek `deepseek-flash`. Переменные: `DEEPSEEK_API_KEY`, `DEEPSEEK_MODEL`, `DEEPSEEK_BASE_URL`. Пример без секрета — `.env.example`. GPU для проверки не нужен.

## 25% — пользовательский опыт

Основной пользователь — стажёр. Кабинет наставника и руководителя показывает прогресс своей команды. Отдельного интерфейса HR BP нет: ограничение кейса это разрешает.

На главной видны этап стажировки и ближайший шаг. Отметка чек-листа сохраняется в браузере и не ждёт модель. Запрос в чат показывает состояние ожидания и отключает повторную отправку. Ответ приходит абзацами, источники — отдельными карточками. Карточка конкретного задания открывает его сервис или инструкцию; общий план подписан отдельно. [Проверенные назначения и границы](ai/chat-navigation-audit.md). Сбой модели или сервиса показывает сообщение «Buddy временно недоступен» и не блокирует остальные экраны.

Ориентир «меньше 1 секунды» относится к простым локальным действиям: переход по разделам и отметка шага. Запрос к модели и корпоративному API занимает больше времени и не держит интерфейс. Медиана локальных действий и появления индикатора ожидания составила менее 50 мс в проверенном браузере. [Методика и результаты](ui-responsiveness.md).

## 20% — работоспособность сценариев

Основной сценарий — заявка на доступ с сохранённым результатом в портале. Дополнительные сценарии перечислены ниже.

| Сценарий | Результат для стажёра |
| --- | --- |
| Команда и инструменты | Ответ про наставника и команду текущего профиля, со ссылкой на источник |
| Задачи Jira | «Мои задачи» читает личные назначения; задачи команды — доступные доски и задачи коллег со ссылками в Jira. Старый разговор о доступах не подменяет чтение каталогом заявок |
| Этап адаптации | Чек-лист по роли, статус шага и следующий пункт |
| Личный календарь | События за неделю или заданные даты со ссылкой на `/events`; создание из чата только после ручного подтверждения, общий источник Go/PostgreSQL для веба и агента |
| Действие в сервисе | Черновик найма, увольнения, бенефита или задачи Jira. Человек подтверждает его на `/actions/:id`. Сервис возвращает результат, страница его сохраняет |
| Разбор пункта адаптации | Кнопка у пункта, общая панель Buddy, смысл и шаги, ссылки на материалы/сервисы, контекст в уточнениях и общая история с полным чатом |
| Кабинет наставника | Прогресс стажёра своей команды и публикация ссылки или файла в браузере |

Сценарий действия завершён, когда стажёр видит сохранённый результат, а не только кнопку. Заявка на доступ может закончиться номером и статусом: прототип не выдаёт настоящие права. Если права нет или сервис не запущен, запись не создаётся.

Подготовка также требует результата инструмента: без receipt текущего хода
текст «черновик готов» не подтверждает наличие карточки. Исправление проверяет
возврат настоящей ссылки `/actions/:id` после такого ложного ответа.

Агент не заменяет наставника. Он снимает повторяющиеся вопросы «что делать» и «как сделать» и оставляет человеку подтверждение действия.

## 15% — техническая реализация

Поведение агента и инструментов описано до кода в `docs/specs/`. Для действия там видно, где человек подтверждает операцию, какой запрос уходит в сервис и какая ошибка возвращается. Формат OpenSpec допустим по ответу организаторов; актуальные спецификации — в `docs/specs/`, каталог `openspec/changes/` хранит прежнее предложение и не заменяет их.

Тесты запускаются командами из README. Отчёт покрытия — [coverage.md](coverage.md). Веб, Python и Go API отдельно прошли порог 80%. Для Go приведены покрытие операторов и расчёт строк по блокам профиля.

## 5% — безопасность и данные

- Чтение и подготовка действия идут от текущего профиля. Чужой диалог и чужая операция не отдаются.
- Модель не выполняет запись. Инструмент готовит неизменяемый черновик, отправка происходит после кнопки подтверждения.
- Повтор подтверждения не создаёт вторую отправку. Неясный ответ сервиса помечается и не отправляется снова.
- Данные синтетические. Учебные инструкции не названы регламентами Авито.
- Сценариев с чувствительными персональными данными и реальными финансовыми операциями нет. Бенефит в прототипе — тестовая заявка, не выплата.
- Разбор пункта использует только чтение: write-tools исключены в Python и запрещены подписанным read_only в Go. Передаются название и ограниченное описание пункта, а не полный DOM или значения форм.
- Ключ модели только в окружении. В ответах агента нет токенов и сырого ответа модели.
- При расхождении доступных инструкций Buddy показывает оба варианта со ссылками и предлагает уточнить порядок у наставника. [Спецификация](specs/conflicting-knowledge.md).

## Метрики пользы

Это предложение, не результат пилота.

Цель прототипа — сократить повторяющиеся организационные вопросы, а не заменить встречи с наставником. Для проверки на стажёрах сопоставимых ролей:

- время от входа до первого подтверждённого действия в сервисе;
- число повторных вопросов наставнику о доступах, команде и первом шаге;
- доля шагов чек-листа, которые стажёр закрывает без отдельного разбора.

Прототип собирает обратную связь после первой недели, на экваторе и в конце стажировки. Для проверки эффекта можно сравнить две группы и результаты анкет. [Сценарий опросов](specs/internship-surveys.md). Технически для сервиса смотрят долю ответов со ссылкой на источник, долю действий, дошедших до подтверждения, и долю запросов, завершившихся явной ошибкой, а не зависанием.

Чистые приветствия отвечаются без корпоративного поиска; вопрос после приветствия
сохраняет обычные требования к источникам и подтверждению действий.

Рекомендация следующего шага использует тот же пункт «В процессе», что веб-чек-лист,
свежий контекст передаётся при отправке. Это не серверное подтверждение этапа.
Buddy поддерживает уважительное неформальное общение без ослабления проверки фактов и операций.

Доступы из чата используют тот же сценарий подтверждения, что Jira:
`get_access_catalog` → `prepare_service_action(request_access)` → карточка
с параметрами → кнопка подтверждения → сохранённый номер. Все шаблоны
каталога проверяются сервером с учётом профиля; уточнение параметров
в следующем сообщении сохраняет контекст заявки.
