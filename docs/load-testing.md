# Нагрузочные тесты без платных вызовов

## После git clone

Нужны Git, POSIX `sh` и Python 3.10+ со стандартной библиотекой. Linux с glibc
и macOS поддерживаются на x64/arm64; для Windows нужен WSL. Docker и just
для этого запуска не требуются.

```bash
git clone https://github.com/dureppa/ai-buddy.git
cd ai-buddy
./load_test.sh                 # 120 операций на сценарий, 8 работников
./load_test.sh 1000 16         # увеличенный прогон
```

Файл исполняемый в Git: вручную вызывать sh, chmod или export PATH не нужно.
Можно запускать из другого каталога: `/путь/к/ai-buddy/load_test.sh 120 8`.
Аргументы имеют приоритет над LOAD_REQUESTS/LOAD_WORKERS.
`LOAD_HISTORY=100 ./load_test.sh 120 8` меняет длину истории чата.
`./load_test.sh --help` показывает справку без подготовки инструментов.

При первом запуске Python-helper скачивает закреплённые Node и Go с официальных
сайтов, а uv — из официального пакета PyPI; проверяет SHA-256 издателя и безопасно
распаковывает архивы в `.load-tools/` внутри проекта. Node берётся из `.nvmrc`,
Go из `web/backend/go.mod`, npm из packageManager, uv закреплён в helper.
uv подготавливает Python нужной версии из `ai-agent/.python-version`.
Нужны интернет, свободное место и время на первую установку. Системные пакеты,
профиль оболочки и глобальный PATH не меняются; sudo не требуется.

SDK, Python и кэши сохраняются в `.load-tools/`, Python-зависимости — в
`ai-agent/.venv`, npm-зависимости — в `node_modules`. Всё это исключено из Git.
Повторный запуск переиспользует инструменты. npm ci выполняется при изменении
манифестов/lock-файла либо отсутствии зависимостей, Go mod download — при
изменении go.mod/go.sum либо отсутствии кэша. uv sync --locked быстро сверяет
окружение и устанавливает только недостающее. Параллельная установка в тот же
checkout запрещена файловой блокировкой, которая снимается при завершении.

Сеть используется для подготовки SDK/зависимостей. Сам прогон использует
тестовые подмены и сетевые запреты frontend/Python; Go не создаёт AI-клиент.
Go/uv работают с подготовленными пакетами в offline-режиме. Скрипт не читает
.env и не передаёт ключи модели дочерним командам. Ключ ИИ и работающие сервисы
не нужны. Ошибка установки или любого теста останавливает запуск с ненулевым
кодом; неверные параметры отклоняются до установки. Вывод можно сохранить:
`./load_test.sh 120 8 > load.log 2>&1`.

Реализация: `load_test.sh` → stdlib-helper `ai-agent/load_bootstrap.py` → общий
`ops/checks/load-suite.sh`. Docker-образов для нагрузочного запуска нет.

## Запуск с установленными языками

Нужны Node.js 24/npm 11, Go и Python из [стека](stack.md). Перед первым запуском
выполни `npm ci` из корня и `uv sync --locked` из `ai-agent`.
Команды из корня репозитория:

```bash
just load-test 120 8           # короткий прогон frontend + Go + Python
just load-test 1000 16         # увеличенный прогон всех трёх контуров
just load-frontend 1000 16     # только frontend
just load-test                # 2000 операций на сценарий, 16 работников
just load-bench                # Go benchmark: ns/op, B/op, allocs/op
```

Работающие сервисы, PostgreSQL и ключ DeepSeek не нужны. Команды создают только
тестовые приложения внутри процессов. Адрес работающего приложения передать
нельзя. Go/Python не читают `.env`; frontend подменяет сетевые зависимости
независимо от настройки API. Тесты не запускают сервер приложения и фоновый
генератор путеводителя. Прикладной код и настройки продуктового запуска не меняются.

## Защита от расхода токенов

Frontend использует настоящий `backend.ts` с тестовым `fetch`, разрешающим только
демосессии и чат. React-компоненты работают с синтетическими данными. Любой иной
fetch, XMLHttpRequest, WebSocket или попытка TCP-соединения через Node Socket
завершает тест ошибкой. Проверка `network=0` выполняется даже при перехваченной
ошибке. Ни работающий Go, ни DeepSeek не вызываются.

Go собирает API с хранилищами в памяти и отдельным `loadAssistant`: вместо
AI-клиента используется синтетический ответ с текстом запроса. HTTP-клиентов
модели в этой конфигурации нет.

Python использует настоящий Flask, `DirectRunner`, обработку ответа DeepSeek,
MCP Gateway и проверку источников. Только транспорт модели заменён
`httpx.MockTransport`, а MCP — отдельной тестовой сессией на каждый ход.
Настройки задаются явно с синтетическим ключом. TCP, UDP и DNS блокируются
в тестовом процессе; даже перехваченная приложением попытка соединения
увеличит `network` и завершит тест ошибкой. Проверяется точное количество
обращений к заглушкам: неожиданный повтор также провалит тест.
Счётчик `model` в отчёте означает вызовы заглушки, реальные обращения к LLM — 0.

## Сценарии и критерии

| Go | Python |
| --- | --- |
| Чек-лист с действующей сессией | Успешный ход с чтением команды и источником `/team` |
| Уведомления | Отказ заглушки провайдера 429 → `AI_RATE_LIMITED` |
| Список заявок | Сбой MCP → `MCP_UNAVAILABLE` |
| Чат с синтетическим ответом | Некорректный запрос → 400 |
| Некорректный чат → 400 | Отсутствие авторизации → 401 |
| Отсутствие авторизации → 401 | Проверка жизни процесса |

Frontend (`web/frontend/src/load.test.tsx`) добавляет пять сценариев:

- Параллельные запросы API-клиента от четырёх профилей: отдельные токены и
  conversation ID, одна демосессия на профиль, точный ответ на каждый вопрос.
- Параллельные HTTP 503: клиент отклоняет запросы, не подставляет демоответ и
  не сохраняет успешный диалог.
- Обновление длинной истории React-чата с форматированием и карточками источников,
  отправка через настоящие события input/submit, очистка поля после отправки.
- Та же история в ожидании ответа: индикатор, заблокированная кнопка и запрет
  повторной отправки даже при программном submit.
- Та же история с ошибкой: видимый alert и работающая кнопка «Повторить».

Каждый DOM-цикл проверяет количество сообщений и источников, экранирование HTML
и отсутствие накопления дубликатов. После сценария React root размонтируется,
контейнер удаляется. `LOAD_HISTORY` задаёт число сообщений истории (по умолчанию
40, допустимо 1–1000), например `LOAD_HISTORY=100 just load-frontend 120 8`.

Каждый сценарий запускает фиксированное число запросов параллельно, после
общего стартового сигнала. Go использует goroutine, Python — потоки с отдельными
Flask-клиентами. Проверяются статус **и содержимое** каждого ответа; ожидаемые
400/401/503 не считаются ошибками нагрузки. Проверяются уникальный текст чата
в Go, соответствие request/conversation ID в Python, отсутствие секретов,
число открытых/закрытых MCP-сессий и количество вызовов заглушек.

В frontend API одновременно выполняется до `LOAD_WORKERS` асинхронных операций.
React DOM обновляется последовательно в одном JS-потоке, поэтому эти сценарии
всегда выводят `workers=1`. Это моделирование одного клиентского интерфейса,
а не нескольких браузеров или параллельных потоков рендеринга.

Неожиданный статус, неверное тело, утечка ID/секрета, лишний вызов или незакрытая
сессия завершают команду ненулевым кодом. Общих аппаратно зависимых порогов
времени нет. Go также запускается с `-race` в обычном CI.

## Метрики и границы замера

Каждый сценарий выводит `LOAD_RESULT`: число запросов, фактическое число
работников, ошибки, RPS, p50/p95/p99 и максимум в миллисекундах. Перцентили —
nearest rank: элемент `ceil(N × p)` отсортированной выборки. RPS — число
обработанных запросов за время всего сценария, включая тестовую проверку ответов.
В Go задержка измеряется вокруг `ServeHTTP`, в Python — вокруг вызова Flask
test client. Время ожидания запроса до начала обработки не учитывается.

Frontend выводит `operations` вместо `requests`; `rps` означает операции в секунду.
Операция API — один вызов клиента с проверкой результата; DOM-операция — обновление
чата, события ввода/отправки или повтора и проверки результата. Её задержка
включает React `act` и assertions. Она не является временем показа кадра.

Это замкнутая нагрузка: каждый работник отправляет следующий запрос после
ответа. Прогрев не выделен, первые запросы включены в результат. Go benchmark
калибруется стандартным `testing.B`. Сравнивай повторные прогоны одного контура
на одинаковом оборудовании и с одинаковыми параметрами. Времена трёх контуров
напрямую несопоставимы: сценарии и границы измерения разные.

Тесты измеряют обработку внутри процесса с синтетическими зависимостями.
Сетевой HTTP, nginx, WSGI/ASGI-сервер, PostgreSQL, самостоятельные корпоративные
API, скорость и качество LLM этим прогоном не измеряются. Эти числа не являются
пропускной способностью развёрнутого приложения или гарантией SLA.
jsdom не выполняет браузерный layout/paint и не измеряет FPS, загрузку JS/CSS,
LCP/INP или потребление памяти. Браузерный замер описан отдельно в
[ui-responsiveness](ui-responsiveness.md). Большие DOM-прогоны могут занять несколько минут.

## Запуск без just и в CI

Без just при подготовленных нативных зависимостях из любого каталога:
`LOAD_REQUESTS=120 LOAD_WORKERS=8 sh /путь/к/ai-buddy/ops/checks/load-suite.sh`.
Этим же общим скриптом пользуются `./load_test.sh` и рецепт `just load-test`.

Frontend из корня:

```bash
LOAD_REQUESTS=1000 LOAD_WORKERS=16 npm run test:load --workspace=@ai-buddy/web
```

Из `web/backend`:

```bash
LOAD_REQUESTS=2000 LOAD_WORKERS=16 go test ./internal/httpapi -run '^TestBackendLoad$' -count=1 -v -timeout=10m
LOAD_REQUESTS=1000 LOAD_WORKERS=16 go test -race ./internal/httpapi -run '^TestBackendLoad$' -count=1 -v
go test ./internal/httpapi -run '^$' -bench '^BenchmarkBackend' -benchmem -benchtime=3s -cpu=1,4,16
```

Из `ai-agent`:

```bash
LOAD_REQUESTS=2000 LOAD_WORKERS=16 uv run --locked pytest tests/test_load.py -q -s
```

`LOAD_REQUESTS`: целое 1–100000 **на каждый сценарий**; `LOAD_WORKERS`: 1–256,
но не больше числа запросов. При некорректных значениях тест завершается ошибкой.
Без переменных выполняется по 120 запросов/операций с 8 работниками на сценарий
(для React DOM — один работник). Обычные `npm test`, `go test ./...` и `pytest`
автоматически подхватывают короткие прогоны в существующих CI jobs
`frontend`, `go` и `python`; большие запуски выполняются явно.
CI `repository` дополнительно выполняет `LOAD_HISTORY=1 ./load_test.sh 2 2`
из чистого checkout. Установка, кэш, контрольные суммы, неверные параметры,
блокировка параллельного запуска и остановка при ошибках проверяются
`ai-agent/tests/test_load_launcher.py` на настоящих shell-скриптах с fake-командами.
Для вывода метрик нужны `-v` у Go и `-s` у pytest. Параллельные короткие прогоны
не заменяют тесты с реальной БД из [стандартов разработки](engineering.md).
