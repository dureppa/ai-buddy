# Управление доступами

Самостоятельный демонстрационный фронт на React/TypeScript/Zod. Сетка карточек
ориентируется на предоставленный пользователем скриншот. Каталог состоит из
девяти шаблонов для аналитиков, бэкендеров, тестировщиков и дизайнеров; общие
ресурсы — Jira и VPN. [Поведение](../specs/006-access-portal.md).

Кнопка в корпоративных сервисах открывает http://localhost:5190 в новой вкладке
с текущим demo profile_id. Адрес задаёт VITE_ACCESS_URL. На сервере ссылка
собирается через PUBLIC_HR_ORIGIN; статический сайт включён в hr-web, поэтому
отдельного Go-контейнера для этого фронтенд-среза нет. Порт 5190 должен быть
доступен пользователю. Nginx применяет тот же парольный gate, что к другим сайтам.

## Запуск и файлы

`npm run dev --workspace=@ai-buddy/corporate-services -- access` — Vite на 5190.
`npm run build --workspace=@ai-buddy/corporate-services` создаёт dist/access.
Compose: `docker compose --profile hr up --build -d`; серверный CD пересобирает
существующий hr-web. Своей БД пока нет: демозаявки живут в localStorage на origin
этого сайта, под ключом ai-buddy.access-portal.v1. Разные браузеры/устройства
не разделяют очередь. Ошибки чтения/записи видны и не выдают ложный успех.

- services/access/frontend/catalog.ts: шаблоны, рекомендации ролям, уровни и поля.
- model.ts: валидация, создание, дубликаты, видимость, согласование и хранилище.
- page.tsx/style.css: каталог, пошаговая форма, сводка, заявки и решения.
- model.test.ts: правила, ошибки, изоляция продуктов, сериализация и поля UI.
- corporate-links.ts/CorporateDirectory.tsx: ссылка из основного веба.

Стажёр создаёт заявку, проверяет сводку и отправляет на согласование. В демопрофиле
руководителя доступны заявки своего продукта; отказ требует комментария.
Смена профиля — учебный переключатель, не production-авторизация. Уведомление
в UI прямо говорит, что согласование не выдаёт реальных прав. Уровни прав
определены шаблоном: DWH только чтение, Git — чтение/запись, dev/stage также
администрирование с отдельным согласованием.

## Будущий агент и API

[OpenAPI-проект](../../contracts/access-portal.openapi.yaml) имеет статус design
only. Живые HTTP/MCP-инструменты и provisioning не реализованы. Формат
RequestInput совпадает с полями демоформы. Контекст личности должен определять
Go, а не LLM или параметры клиента.

1. Агент читает доступные шаблоны через Go/MCP, учитывая продукт/команду/должность.
2. Уточняет ключ ресурса, обоснование, права, срок и поля конкретного шаблона.
3. prepare_access_request создаёт серверный черновик. Ничего не выдаётся.
4. Пользователь подтверждает сводку. Go проверяет владельца, актуальную версию
   каталога/черновика и срок; Idempotency-Key предотвращает повторную заявку.
5. Сервис доступов выбирает согласующих. После согласования отдельный адаптер
   выполняет выдачу (например, добавление участника в Jira) и проверяет результат.
6. read_access_requests возвращает реальные статусы. Только provisioning даёт
   granted; LLM не может поставить его самостоятельно.

Примеры для диалога: «Нужна витрина delivery.orders_mart на чтение для анализа
воронки», «Нужна запись в travel/booking-api для исправления проверки дат»,
«Нужны фикстуры VIN в stage для регресса», «Нужна запись в Figma-проект инициатив».
Существующие baseline-заявки SDD 001 остаются отдельным механизмом до реализации
серверной интеграции; этот фронт их не подменяет.

## Проверки

Новые тесты включены в corporate-services Vitest, типизацию и frontend job CI.
`just frontend-check` выполняет форматирование, ESLint, TypeScript, тесты и сборки.
Регрессия в вебе проверяет наличие ссылки и передачу profile_id без токена.
