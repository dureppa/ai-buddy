# Сервис доступов: демонстрационный фронт

Новый самостоятельный сайт «Управление доступами» на 5190 открывается в новой
вкладке из корпоративных сервисов с активным аккаунтом Buddy. Визуальный ориентир —
предоставленный пользователем скриншот: сетка белых карточек с цветными иконками.

Каталог: аналитика (витрины DWH, BI), разработка (репозитории, dev/stage и логи),
тестирование (тестовые среды и обезличенные данные), дизайн (Figma и исследования),
общие инструменты (Jira, VPN, группы, диски). Каждая карточка определяет допустимые
права и дополнительные поля. Название системы и ключ конкретного ресурса обязательны,
как обоснование (10–2000 символов), уровень read/write/admin и срок 1–90 дней.
Недоступные уровни не предлагаются; admin всегда требует отдельного согласования.
Например, DWH не предлагает запись и admin, репозиторий — чтение/запись.

Контекст продукта/команды/должности выводится из выбранного демопрофиля. Стажёр
видит рекомендуемые категории и общий каталог; поиск работает по названию и описанию.
Форма запоминает введённые значения при ошибке. Перед отправкой показывает сводку.
Заявки сохраняются в localStorage отдельно от прежних Buddy-заявок. Возможны
статусы submitted, approved, rejected, cancelled. Одобрение заявки не означает
выдачу реальных прав: provisioning не подключён, это явно написано в интерфейсе.
Повторная активная заявка на тот же ресурс/права не создаётся. Отмена доступна
только владельцу. Руководитель рассматривает submitted-заявки своей команды,
не свои; при отказе требуется комментарий. Общая demo-cookie Buddy не является
аутентификацией или защитой данных; production-проверки должны выполняться в Go.
Сбой хранилища показывается как ошибка; UI не сообщает об успешной записи.
Повреждённое сохранение не перезаписывается незаметно.

Подключение агента — проект контракта, не реализованный API/MCP. Один формат
AccessRequestInput для формы и агента: template_id, system, resource_key,
justification, permission, duration_days, fields, catalog_version. Go получает
пользователя из сессии, проверяет контекст и конфигурацию, создаёт черновик;
пользователь подтверждает неизменённую сводку. Подтверждение привязано к владельцу,
версии и сроку, повтор идемпотентен. Агент не задаёт себе должность или права.
Обязательные поля уточняются; неизвестный template/ключ отклоняется; источники
текста задач не могут предоставлять разрешения. Согласование и provisioning
отделены: только подтверждённое изменение в целевой системе даёт статус granted.
Будущий API: contracts/access-portal.openapi.yaml. Текущий SDD 001 остаётся
baseline и не меняет контракт в этом фронтенд-срезе.
